# Spec — D3 짧은 표 합치기 실험 (청킹 개선)

상태: **측정 완료, 미채택** (2026-11-03). 결정 D1~D4를 확정했다.

## 결론

같은 절 안에서 연속된 짧은 라벨 조각과 표 조각을 1,000자 안에서 합친다. 주 변형은 **200자 미만 + 표 앞 짧은 소개 문장 포함**이다. 16개사 청크는 9,815개에서 7,956개, 고유 본문은 8,759개에서 7,504개가 되고, 100자 미만 비율은 39.3%에서 23.6%로 내려간다(시제품 실측).

표는 라벨을 얻지만 **구제가 보장되지는 않는다.** 9번 정답에는 "주요 고객"과 "당기"가 들어오고, 10번 정답 중 87은 "외화"와 "10% 변동"이 들어온다. 10번 정답 81은 "외화" 설명이 484자 문단에 있어 합쳐지지 않는다.

청크가 바뀌면 모든 `chunk_id`가 바뀌므로, 정답은 본문 포함 규칙으로 옮긴다. 시제품에서 정답 34개 모두 후보 1개로 매핑됐다. 동결 파일은 수정하지 않는다.


## 측정 결과

주 변형은 **채택하지 않는다.** 모드와 매핑 코드는 남기되 기본값은 `group` 그대로다.

- **참고 변형이 같은 이유**: top-10의 147/150자리가 본문까지 그대로다. 상위권은 원래 긴 청크가 차지해, 짧은 조각을 합쳐도 그 자리까지 올라오지 못한다. 공통 본문의 벡터는 코사인 0.9999998 이상으로 같다.
- **주 변형의 악화**: 합쳐진 소개 문장 묶음이 상위에 들어오면서 정답을 밀어냈다. top-10의 합쳐진 조각은 11개다.
- **top-100 참고(판정 대상 아님)**: 10번 정답이 top-100 밖에서 **21위**로 올라왔다. 9번은 여전히 top-100 밖이다. Recall@30·50은 베이스라인 0.867, 주 변형 0.933이다.
- **후속 후보**: 주 변형은 후보 안의 정답을 늘리지만 순서는 나빠진다. 순서를 고치는 리랭커와 결합할 때 의미가 있을 수 있다. 다만 이것은 새 실험이며 사전 등록이 필요하다.
- **구현 중 발견**: 겹침 제거가 단어 중간을 잘라 4개 문서를 손상시켰으나, 재빌드의 보존 검사가 임베딩 전에 잡았다. 수정 후 `truncated` 0건, 옛 16개사 청크 누락 0건이다.
- **산출물**: `evals/results/merge_e5_v1.jsonl`, `mergetable_e5_v1.jsonl`과 지표, `evals/mappings/`. 정답 34개 모두 `exact`로 매핑됐고, 주 변형에서 12번 정답 2개가 한 청크로 합쳐졌다. 임베딩은 CPU로 약 21건/초, 각 6분이었다.

## Why

- **페르소나**: 체크리스트 항목별 근거를 찾는 기업여신 심사역
- **상황**: v7(`dart_xml_v7`, `table_mode=group`)은 100사 전체에서 100자 미만 청크가 44.1%, 16개사에서 39.3%다.
- **문제**:
  1. 파서가 제목, `당기 | (단위 : 천원)` 라벨, 숫자 표를 서로 다른 표(`table_group`)로 낸다. 기존 표 묶음은 같은 `table_group` 안에서만 합치므로 붙지 않는다.
  2. 숫자 조각만으로는 무엇에 대한 값인지, 당기인지 전기인지 알 수 없다. 9·10번 정답이 top-100에도 없는 이유로 보인다.
  3. 머리말(#39)과 이웃 조각(#41)은 입력이나 결과를 덧붙이는 방식이라 채택되지 않았다. 이번에는 청크 자체를 고친다.
- **측정 지표**: Recall@10, MRR@10, 9·10번 첫 정답 순위, 나아진·나빠진 문항 수, top-10 총 글자 수, 청크 수

## Goal

- **해결 목표**: 라벨과 숫자가 한 청크에 들어가게 해 짧은 표의 검색 가능성을 높인다.
- **성공 기준(채택 기준)**: 주 변형이 아래를 모두 만족하면 채택한다.
  1. Recall@10 +0.067 이상(0.800 이상), 또는 MRR@10 +0.05 이상(0.458 이상)
  2. Recall@10과 MRR@10이 둘 다 베이스라인보다 낮지 않음
  3. 첫 정답 순위가 나아진 문항이 나빠진 문항보다 2개 이상 많음
  4. 9·10번 중 1개 이상 top-10 진입
  5. top-10 평균 총 글자 수가 베이스라인(6,670자)의 1.1배(7,337자) 이하
- **Out of Scope**: 리랭커, BM25, 머리말, 이웃 조각, 최종 100사 재선정, 파서 변경, 긴 표 분할 변경, 전년판, 스냅샷 재생성, 평가셋 수정

## What

**Happy Path**

1. `ingest build --table-mode group_merge_short`로 100사 전체를 다시 빌드한다. 상용구 제거가 회사 간 비교라 16개사만 빌드하면 결과가 달라진다.
2. 16개사를 `--corp-codes`로 골라 e5-small로 임베딩한다.
3. 옛 정답을 본문 포함 규칙으로 새 청크에 매핑한다.
4. 매핑한 파생 평가 파일로 `offline_eval`을 실행한다.
5. 베이스라인과 문항별로 비교한다.

**합치기 규칙**

| 항목 | 규칙 |
|---|---|
| 대상 | 200자 미만인 표 청크. 그리고 바로 다음이 같은 절의 표인 200자 미만 문단(소개 문장, D2) |
| 라벨 | 절 제목 접두사를 뺀 본문에 두 자리 이상 숫자가 없는 조각 |
| 데이터 | 라벨이 아닌 표 조각 |
| 묶음 | `[소개 문장] [라벨 0개 이상] [데이터 1개]`. 한 묶음에 데이터는 하나만 |
| 새 묶음 시작 | 데이터가 있는 묶음 뒤에 라벨이나 데이터가 오면 끊는다. 그래서 `당기` 표와 `전기` 표는 합쳐지지 않는다 |
| 경계 | `chapter`, `section_path`, `note_no` 중 하나라도 다르면 끊는다 |
| 상한 | 합친 결과가 `max_chars`(1,000자)를 넘으면 끊는다 |
| 순서 | 원래 ordinal 순서 그대로 |
| 본문 조립 | 첫 조각은 그대로, 뒤 조각은 절 제목 접두사를 뺀다. 뒤 조각이 직전 본문으로 시작하면 겹치는 부분은 한 번만 쓴다 |
| 메타데이터 | 첫 조각의 값을 쓰고 `is_table=true`. ordinal은 합친 뒤 1부터 다시 매긴다 |

- **다른 표의 제목을 붙이지 않는 방법**: 라벨은 뒤따르는 데이터에만 붙고, 데이터 뒤에서는 항상 끊는다. 데이터끼리 합치는 변형은 고유 본문이 33개만 줄어 효과가 작고 다른 표를 섞을 위험이 있어 제외한다.
- **이름**: 주 변형은 `table_mode=group_merge_short`, 표·라벨만 합치는 참고 변형은 `group_merge_short_table`이다. 파서는 그대로이므로 `dart_xml_v7`을 유지한다. `table_mode`는 `corpus_id` 해시에 들어가므로 새 `corpus_id`가 자동으로 생긴다.
- **기존 모드**: `group`, `row`, `group_drop_numeric`의 결과는 바뀌지 않는다.

**Edge Cases**

| # | 상황 | 처리 방식 |
|---|---|---|
| EC-01 | 라벨 뒤에 데이터 없이 절이 끝남 | 라벨끼리만 묶어 그대로 둠 |
| EC-02 | 소개 문장 뒤가 200자 이상 표 | 합치지 않음 |
| EC-03 | 200자 이상 표 앞의 라벨 | 합치지 않음. 긴 표는 이번 대상이 아님 |
| EC-04 | 합치면 1,000자 초과 | 그 앞에서 끊음 |
| EC-05 | 조각 하나만 남은 묶음 | 본문을 바꾸지 않음 |
| EC-06 | 정제 후 빈 본문 | 기존처럼 건너뜀 |

## How

### 시제품 실측 (저장소 밖, 임베딩·점수 계산 없음)

| 규칙 | 16개사 청크 | 고유 본문 | 100자 미만 | 200자 미만 | 합쳐진 청크 | 100사 청크 |
|---|---:|---:|---:|---:|---:|---:|
| 현재 v7 | 9,815 | 8,759 | 39.3% | 50.8% | 0 | 60,824 |
| 100자 미만, 표·라벨만 | 9,054 | 8,182 | 32.3% | 46.6% | 664 | 55,333 |
| 200자 미만, 표·라벨만 (참고) | 8,477 | 7,844 | 27.9% | 41.5% | 1,094 | 50,629 |
| **200자 미만, 소개 문장 포함 (주 변형)** | **7,956** | **7,504** | **23.6%** | **36.3%** | **1,467** | **46,906** |
| 300자 미만, 소개 문장 포함 | 7,370 | 7,066 | 18.8% | 31.7% | 1,888 | 43,181 |

시제품은 기존 청크 파일에 규칙을 적용한 값이다. 실제 빌드에서 주 변형은 16개사 7,956개, 고유 본문 7,504개, 100자 미만 23.8%, 200자 미만 36.6%, 100사 46,900개였고, 참고 변형은 8,477개, 7,844개, 28.1%, 41.7%, 50,629개였다. 100자 기준은 10번 정답 81(102자)을 놓치므로 쓰지 않는다. 임계값을 정답 조각 길이를 본 뒤 정했다는 점은 PREREGISTER의 "이미 본 숫자"에 적는다.

### 9·10번 적용 예시

**9번** (`ordinal 1062~1064` → 합침, 102자에서 겹침을 빼면 85자)

```text
25. 고객과의 계약에서 생기는 수익 주요 고객에 대한 정보의 공시 당기 | (단위 : 천원) A사 고객과의 계약에서 생기는 수익 | 46,589,675
```

"주요 고객"과 "당기"가 같은 청크에 들어온다. 뒤따르는 `전기` 표(1065~1066)는 별도 청크가 된다.

**10번 정답 81** (`ordinal 80~81` → 합침, 113자)

```text
5. 위험관리 및 파생거래 (단위 : 백만원) 통 화 | 자산(원화환산액) | 부채(원화환산액) USD | 25,803 | 25,586 기타 통화 | - | 754 합 계 | 25,803 | 26,340
```

단위만 들어오고 **"외화" 설명은 없다.** 그 설명은 484자 문단(ordinal 79)이라 대상이 아니다.

**10번 정답 87** (`ordinal 85~87` → 합침, 161자)

```text
연결실체는 내부적으로 환율변동에 따른 환위험을 정기적으로 측정하고 있습니다. 당기말 및 전기말 현재 주요 외화에 대한 원화환율의 10% 변동 시 당기손익에 미치는 영향은 다음과 같습니다. 1 당기말 (단위 : 백만원) 통 화 | 10% 상승시 | 10% 하락시 USD | 16 | (16)
```

소개 문장을 포함할 때만 이렇게 된다. 표·라벨만 합치면 ordinal 86~87까지만 묶이고 "외화"는 들어오지 않는다.

### 정답 매핑

**왜 규칙으로 옮기는가.** `chunk_id`는 `rcept_no`, ordinal, 본문 해시로 만든다. 앞쪽에서 한 번이라도 합치면 뒤 ordinal이 모두 밀려, 본문이 그대로인 1번 정답(ordinal 785)도 id가 바뀐다. 번호로 된 정답은 코퍼스가 바뀌면 죽는다. 근거는 강의 1주13의 "정답셋을 문서 번호가 아니라 규칙으로 정의하면 코퍼스 변경에도 살아남는다"이다(개인 노트 P08 R3. 원본 노트북은 지금 경로에 없어 원문은 미확인).

**파일**: 동결된 `evals/dataset_v1.jsonl`은 수정하지 않는다. 대신 아래 두 파일을 만든다.

| 파일 | 내용 |
|---|---|
| `evals/mappings/short_merge_v1.gold_map.json` | 옛 `chunk_id` → 새 `chunk_id`, 판정 종류, 동결 데이터셋 해시, 옛·새 청크 파일 해시 |
| `evals/mappings/dataset_v1.short_merge.jsonl` | 동결 파일에서 `gold_chunks`, `corpus_version`만 바꾼 파생 평가 파일 |

**매핑 규칙** (측정 전 고정)

1. 옛 청크 본문에서 절 제목 접두사를 뺀 값을 B라 한다.
2. 같은 `rcept_no`, 같은 `section_path`의 새 청크 중 본문에 B가 포함된 것이 후보다.
3. 후보 수에 따라 처리한다.

| 경우 | 처리 |
|---|---|
| 후보 1개 | 매핑. 판정 `exact` |
| 후보 2개 이상 (같은 본문 반복) | 옛 청크의 문서 순서와 일치하는 후보를 고름. 판정 `ordered`, 파일에 기록 |
| 후보 0개 (누락) | **측정 중단.** 규칙 오류로 보고 사용자에게 보고한다. 해당 정답을 빼거나 임의로 고치지 않는다 |
| 쪼개짐 (옛 본문이 새 청크 여러 개에 나뉨) | 합치기만 하는 규칙이라 생기면 안 되므로 **측정 중단** |
| 옛 정답 여러 개가 새 청크 하나로 합쳐짐 | 하나로 매핑. 문항의 정답 수가 줄며 파일에 기록 |

- 시제품(주 변형)에서 정답 34개 모두 후보 1개였고 출처 ordinal과 일치했다. 합쳐진 정답은 9개, 같은 청크로 합쳐진 정답 쌍은 12번 1쌍이다.
- 정답을 사람이 다시 판정하지 않는다. 새 청크는 옛 정답 본문을 그대로 포함하므로 정답의 의미가 유지된다는 전제이고, 이 전제는 AC로 검사한다.
- 정답이 든 청크가 커지면 맞히기가 쉬워진다. 그래서 top-10 총 글자 수를 채택 조건에 넣었다.

### 고정 조건과 소요 시간

- 고정: 모델 e5-small, 16개사, 동결 v1(매핑만), `evals/filters_v1.jsonl`, k=10, `max_length=512`, 배치 64.

- 100사 재빌드: 약 2분(W1.8 실측).
- 임베딩 7,504행:

| 기준 | 처리 속도 | 소요 시간 |
|---|---:|---:|

### 채택 시 후속 영향

- 동결 v1의 공식 정답은 그대로이므로 EVAL_REPORT에 매핑 사용을 밝힌다. v2는 채택된 청크로 정답을 판정해야 한다.

## AC (Given-When-Then)

**AC-SM-01 · 라벨과 데이터 합치기**
- GIVEN: 같은 절의 제목 라벨, `당기` 라벨, 숫자 표가 이어진 블록
- WHEN: `table_mode=group_merge_short`로 청킹
- THEN: 세 조각이 한 청크가 되고, 절 제목은 한 번만 나오며, 숫자가 보존된다

**AC-SM-02 · 다른 표와 분리**
- GIVEN: `당기` 라벨·숫자 뒤에 `전기` 라벨·숫자가 이어짐
- WHEN: 청킹
- THEN: 청크 2개가 되고 `전기`는 첫 청크에 없다

**AC-SM-03 · 경계와 상한**
- GIVEN: `section_path`나 `note_no`가 다른 짧은 표, 합치면 1,000자를 넘는 표, 200자 이상 표
- WHEN: 청킹
- THEN: 합쳐지지 않고 모든 청크가 1,000자 이하다

**AC-SM-04 · 기존 모드 호환**
- GIVEN: 같은 블록
- WHEN: `table_mode=group`으로 청킹
- THEN: 결과가 이번 변경 전과 같고, `data/chunks.100-b-v7.jsonl`을 재현한 빌드의 `chunk_id`와 본문이 그대로다

**AC-SM-05 · 정답 매핑**
- GIVEN: 옛 청크와 새 청크
- WHEN: 매핑 실행
- THEN: 후보 1개는 `exact`, 반복 본문은 문서 순서로 `ordered`가 되고, 모든 매핑에서 새 청크가 옛 본문을 포함한다

**AC-SM-06 · 매핑 실패 중단**
- GIVEN: 어떤 새 청크에도 없는 정답
- WHEN: 매핑 실행
- THEN: 오류로 중단하고 파생 파일을 쓰지 않는다

**AC-SM-07 · 동결 보존**
- GIVEN: 측정 완료
- WHEN: `freeze.py --check`와 `git diff`
- THEN: 동결 파일이 그대로이고, 파생 파일에는 동결 데이터셋 해시가 기록돼 있으며, `gold_chunks`와 `corpus_version` 외의 필드가 같다

**AC-SM-08 · 내용 보존**
- GIVEN: 새 청크 파일
- WHEN: 검증
- THEN: 옛 16개사 청크 본문이 모두 새 청크에 들어 있고, `chunks_preserve_blocks` 검사를 통과한다
