# 사업보고서 연간 갱신 파이프라인 설계

> 상태: 장기 설계만 기록한다. WBS v4에서는 증분 수집과 자동 스케줄러를 구현하지 않는다.

## Why

- **사용자**: 매년 새 사업보고서를 검색해야 하는 기업여신 심사역과 코퍼스 운영 담당자.
- **문제**: 현재 수집·빌드 명령은 선택한 코퍼스 디렉터리의 모든 문서를 다시 읽어 파싱·청킹하고, 전체 manifest·chunks 파일과 새 `corpus_id`를 만든다. 새 보고서 하나를 DB에 Upsert하는 것만으로 안전한 증분 갱신이 되지 않는다.
- **정확한 코드 위치**: 가이드에서 말하는 `build.py`는 현재 저장소의 `backend/rag/ingest.py`에 있는 `build_corpus()` 및 `python -m backend.rag.ingest build`에 해당한다. `backend/graph/build.py`는 질의 실행 그래프이며 코퍼스 생성 코드가 아니다.
- **측정 대상**: 변경 문서 선별 수, 원문·청크 해시 일치, 검색 가능한 정정 전 문서 수, 기간 거절 및 회사·연도 필터 회귀 결과.

## Goal

- **현재 결정**: WBS v4 단계에는 파이프라인 설계 문서만 추가한다. 다음 사업연도를 반영할 때는 키 소유자가 **수동 배치 실행 → 검증 → 전환 승인** 순서로 처리한다.
- **장기 목표**: 동일한 원문과 처리 설정을 가진 문서의 불필요한 재임베딩을 피하면서, 새 보고서·기재정정과 설정 변경을 구분해 새 코퍼스 버전을 검증한 뒤 검색 대상으로 전환한다.
- **장기 성공 기준**: 동일한 원문·설정의 불필요한 재임베딩 0건, 정정 전 보고서의 현행 검색 결과 0건, 검증 실패 버전의 전환 0건, 기간 거절과 회사·사업연도 필터 회귀 시험 전부 통과.
- **Out of Scope (WBS v4)**: 증분 수집 구현, 자동 일정 실행(Airflow·cron), 운영 DB 자동 전환, FY2024 비교용 30건 추가, 동결 평가셋 v1·v2 수정. 현재 코드는 이 문서만으로 증분 갱신을 지원하게 되지 않는다.

## What

### 현재 구현과 한계

1. `backend/rag/dart_client.py`는 키 소유자가 OpenDART의 공시검색 결과를 조회하고 `rcept_no`별 원본 ZIP을 로컬 `data/corpus/<rcept_no>/`에 저장할 수 있다. 서비스 런타임과 CI는 OpenDART를 호출하지 않는다.
2. `backend/rag/ingest.py::build_corpus()`는 코퍼스 디렉터리 전체를 순회해 문서를 파싱하고, 문서 집합 전체에 대한 상용구·전년 유사 문장 판정을 수행한 뒤 manifest·chunks를 통째로 다시 쓴다.
3. `backend/rag/vector_store.py`에는 `ON CONFLICT` Upsert가 있지만 **완성된 manifest·chunks·임베딩 파일 전체**를 입력받는다. 변경 문서만 찾거나, 새 버전을 검증한 후 활성 버전을 원자적으로 바꾸는 기능은 없다.
4. 현재 `corpus_id`는 문서 목록·원본 해시뿐 아니라 `collected_at`과 파서·청킹·임베딩 설정으로 계산된다. 같은 ZIP을 다시 수집해도 수집 시각이 바뀌면 버전 ID가 달라질 수 있다. 장기 구현에서는 수집 시각을 감사 정보로 보관하되 내용 버전 판정과 분리해야 한다.
5. `documents`는 `rcept_no`가 기본키인 전역 테이블이고, `chunks`는 `corpus_id`로 구분된다. 여러 코퍼스 버전의 정정 상태를 독립적으로 보관하려면 문서의 버전별 포함·활성 상태와 검색의 활성 `corpus_id` 선택을 명시적으로 설계해야 한다.

### 장기 갱신 흐름

1. **DART 확인**: 키 소유자가 공시검색 `list.json`에서 정기공시의 사업보고서(`pblntf_ty=A`, `pblntf_detail_ty=A001`)를 조회한다. `last_reprt_at=N`으로 원본과 정정 제출을 함께 확인하고, `[기재정정]`과 새 `rcept_no`를 식별한다. 본문 변경이 없는 `[첨부정정]`·`[첨부추가]`는 별도로 판정한다.
2. **원본 보관**: 처리 대상의 `document.xml` 원본 ZIP을 `rcept_no`별로 저장하고 SHA-256(`raw_sha256`)을 계산한다. 접수일(`filed_at`)과 사업연도(`fiscal_year`)는 별개 필드로 보존한다. API 키나 키가 든 URL은 파일·로그에 남기지 않는다.
3. **Delta Check**: 기존 목록과 `rcept_no`, `raw_sha256`, 파서 버전, 청킹 규칙, 임베딩 프로필(모델·차원·전처리)을 비교한다. 동일하면 원문·벡터를 재사용 후보로 분류하고, 신규·정정·설정 변경은 처리 대상으로 분류한다.
4. **선택 처리**: 신규·내용 변경 문서는 파싱·청킹한다. 파서/청킹 설정 변경 시 영향받는 문서를 다시 처리하고, 임베딩 프로필이 바뀌면 기존 벡터를 그대로 재사용하지 않는다. 같은 본문 해시와 같은 임베딩 프로필의 벡터만 재사용할 수 있다.
5. **전체 일관성 점검**: 상용구 제거와 근접 중복 표시는 문서 집합에 의존하므로, 새 문서만 처리했더라도 기존 문서의 해당 판정이 바뀌는지 검사한다. 바뀌면 관련 문서의 청크 메타데이터와 검색 인덱스를 새 버전에 맞게 다시 만든다.
6. **정정 처리**: 새 정정 보고서가 기존 보고서를 대체한다는 관계를 확인한 뒤, 이전 ZIP과 manifest 기록은 보존하고 새 버전에서는 이전 보고서에 `superseded=true`를 적용한다. 현행 검색은 정정 전 청크를 반환하지 않아야 한다.
7. **검증 후 전환**: 새 `corpus_id`를 별도 버전으로 준비하고 문서 수, 원본·청크·임베딩 해시, 실패 문서, 고유 청크 수와 표본 원문 대조를 확인한다. 전부 통과해야 검색의 활성 버전을 전환하며, 실패하면 기존 버전을 유지해 롤백할 수 있어야 한다.
8. **지시문 연도 갱신**: 주제 판정 지시문의 날짜 문장(85번, '사업보고서는 이미 공시된 과거 실적')은 `backend/services/llm.py`의 `CORPUS_FISCAL_YEAR`에서 계산된다. 새 사업연도로 바꿀 때 이 값을 같이 바꾸고 주제 판정을 다시 잰다(지시문이 바뀌므로 사전 등록 대상). manifest의 사업연도와 다르면 `tests/test_llm_service.py::test_corpus_fiscal_year_matches_manifest`가 실패한다.
9. **회귀 시험**: 미적재 사업연도 질문은 `PERIOD_NOT_IN_CORPUS`로 거절하고, 적재된 회사·사업연도 질문은 다른 회사·연도의 청크를 섞지 않는지 확인한다. 정정 전 보고서가 검색되지 않는지도 확인한다.

## How

### 이번 단계에서 실행하는 정책

- WBS v4의 `뺄 것`에는 **증분 수집(+5)**과 **FY2024 30사·전년 비교**가 있다. 현재 서비스 범위는 FY2025 사업보고서이며, 장기 흐름은 구현 계획을 보존하기 위한 설계다.
- 새 사업연도를 실제로 지원하기로 팀이 결정한 시점에는 먼저 대상 회사·사업연도·보고서 유형과 평가 기준을 확정한다. 키 소유자가 로컬에서 대상 목록을 확인하고 ZIP을 수동 수집한 뒤, 현재의 전체 빌드·검증 배치를 실행한다. 파서·청킹·임베딩 설정과 결과 해시를 기록하고, 검색 필터·기간 거절을 확인한 후 배포를 승인한다.
- 현재 코드에는 활성 버전 전환 명령이 없으므로 **검증 전 자동 전환을 가정하지 않는다**. 검색 버전 선택, 원자적 전환·롤백, 정정 관계 및 벡터 재사용 저장 구조는 증분 구현 단계에서 별도 Spec과 테스트가 필요하다.
- `SPEC.md`와 기존 `docs/specs/d1-dart-ingest.md`에는 WBS v4 이전의 FY2024/+5 범위가 남아 있다. 이 문서는 WBS v4의 현재 실행 범위를 기록하며, 제품 범위의 정본인 `SPEC.md`와의 일치는 팀 결정 후 별도 정리해야 한다.

### 근거

- 프로젝트 코드: `backend/rag/dart_client.py`, `backend/rag/ingest.py`, `backend/rag/vector_store.py`, `backend/rag/chunking.py`, `db/02_schema.sql`.
- 프로젝트 결정: `WBS_1조_v4_20261105.xlsx`의 `뺄 것` 시트, `AGENTS.md`의 동결 평가셋·키 관리 원칙.
- OpenDART 공식 문서: [공시검색 API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001) (`A001`, 정정 포함 검색, `rcept_no`)와 [공시서류원본파일 API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019003) (`document.xml`, ZIP).

## AC (Given-When-Then)

- **AC-01 · 현재 범위** — GIVEN WBS v4 단계 WHEN 이 설계를 검토 THEN 증분 수집·스케줄러 구현과 FY2024 적재는 작업 목록에 추가되지 않고, 수동 배치·검증 원칙만 기록된다.
- **AC-02 · 동일 문서** — GIVEN 원본 SHA-256과 파서·청킹·임베딩 프로필이 모두 같은 문서 WHEN 장기 Delta Check를 실행 THEN 불필요한 파싱·재임베딩 0건으로 분류한다. 단, 문서 집합에 의존하는 중복·상용구 판정은 재확인한다.
- **AC-03 · 정정공시** — GIVEN 같은 회사·사업연도의 정정 보고서와 이전 보고서 WHEN 새 코퍼스 버전을 검증해 활성화 THEN 이전 원본은 남고 이전 청크의 현행 검색 반환은 0건이다.
- **AC-04 · 설정 변경** — GIVEN 파서·청킹 또는 임베딩 프로필이 바뀜 WHEN 새 버전을 준비 THEN 영향받는 문서를 재처리하고 서로 다른 프로필의 벡터를 재사용하지 않는다.
- **AC-05 · 검증 실패** — GIVEN 새 버전에 파싱 실패·해시 불일치·원문 보존 실패가 있음 WHEN 전환을 요청 THEN 활성 코퍼스는 이전 버전으로 유지된다.
- **AC-06 · 검색 회귀** — GIVEN 새 연도를 수동 반영하고 검증함 WHEN 미적재 기간 질문과 회사·사업연도가 서로 다른 두 단일 질문을 시험 THEN 미적재 기간은 거절되고 각 검색 결과는 요청한 회사·사업연도로만 제한된다.
