# Spec — W2.7 로그인 (자체 users + JWT HttpOnly 쿠키)

설계 근거: SDD §5.6, SPEC.md §3.4(`users`)·§5.7(신뢰 경계)·§6(API).

## Why

- **페르소나**: 기업여신 심사역, 그리고 평가용 계정 2개로 접속하는 평가자
- **상황**: 심사 건(`reviews`)·thread·Store namespace는 모두 `user_id`로 나뉜다(SPEC §3.5). 지금은 `current_user_id()`가 `NotImplementedError`라 사용자를 식별할 수 없다.
- **문제**:
  1. 사용자를 구분하지 못하면 G4(두 사용자의 대화와 기억이 섞이지 않음)를 시연할 수 없다.
  2. 이후 라우터가 재사용할 인증 의존성이 없다.
  3. 로그인 응답으로 계정 존재 여부를 알아낼 수 있으면 안 된다.
- **측정 지표**: 평가용 계정 2개 로그인 성공, AC 전체 테스트 통과, 응답·로그의 비밀번호 노출 0건

## Goal

- **해결 목표**: 시드된 계정이 로그인하면 8시간 유효한 세션 쿠키를 받고, 다른 라우터는 `Depends(current_user_id)`로 사용자 id를 얻는다.
- **성공 기준**:
  - 세션 쿠키 수명 28,800초, 속성 `HttpOnly; Secure; SameSite=Lax; Path=/`
  - 틀린 비밀번호와 없는 이메일의 상태 코드·`code`·`message`·`details`가 같다(`request_id`만 요청마다 다름)
  - 계정이 없을 때도 bcrypt 비교를 정확히 1회 수행한다
  - `tests/test_auth.py`가 DB 없이 통과한다
- **Out of Scope**: 가입, 비밀번호 재설정·변경, 이메일 인증, 토큰 폐기 목록, 리프레시 토큰, 로그인 시도 제한, 요청 본문 64KB 상한(SPEC §4, 공통 미들웨어로 별도 작업)

## What

**Happy Path**

1. 운영자가 `scripts/seed_users.py`로 데모 계정 2개를 넣는다.
2. 사용자가 `POST /api/v1/auth/login`을 호출하면 서버가 이메일을 소문자로 바꿔 조회하고 bcrypt로 검증한다.
3. 서버가 HS256 JWT(`sub`, `iat`, `exp`)를 만들어 `session` 쿠키로 내려준다(204).
4. 이후 요청에서 `current_user_id`가 쿠키를 검증해 `user_id`를 돌려준다.
5. `POST /api/v1/auth/logout`이 쿠키를 지운다(204).

**Edge Cases**

| # | 상황 | 처리 방식 |
|---|---|---|
| EC-01 | 없는 이메일 | 더미 해시와 1회 비교한 뒤 틀린 비밀번호와 같은 401 |
| EC-02 | 이메일 대소문자 혼용 | 소문자로 정규화해 조회 |
| EC-03 | 72바이트를 넘는 비밀번호 | 500이 아니라 401. bcrypt 5는 초과 입력에 `ValueError`를 내므로 72바이트로 잘라 비교(시간 유지)하되 결과는 항상 불일치. 시드 스크립트는 초과 비밀번호를 거부한다 |
| EC-04 | 필드 누락·타입 오류·깨진 JSON | 400 `VALIDATION_ERROR`. `details`에 필드 위치와 오류 종류만 담고 입력값은 돌려주지 않는다 |
| EC-05 | 위조·만료·`alg=none`·필수 클레임 누락·`sub`가 UUID가 아닌 토큰 | 401 `AUTH_REQUIRED` |
| EC-06 | 유효한 토큰이지만 사용자가 삭제됨 | `/me`는 401. `current_user_id`만 쓰는 라우터는 DB를 조회하지 않으므로 토큰 만료 전까지 통과한다(아래 제약) |
| EC-07 | `AUTH_SECRET` 없음·32바이트 미만 | 앱 기동 실패, 이름을 밝힌 오류 메시지. compose만 비어 있을 때 컨테이너 시작 시 무작위 값을 만들어 G2를 지킨다 |
| EC-08 | DB 장애 등 예상 못 한 오류 | 500 `INTERNAL_ERROR`, 공통 오류 형식. 내부 메시지를 본문에 넣지 않는다. DB 장애를 `SERVICE_UNAVAILABLE_DB`로 구분하는 것은 이 Spec에서 구현하지 않는다 |
| EC-09 | 이메일에 NUL 문자 | PostgreSQL이 받을 수 없으므로 조회 없이 "없는 계정"으로 처리 |

## How

```
POST /api/v1/auth/login
요청: { "email": string, "password": string }
성공 204, Set-Cookie: session=<JWT>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=28800
실패 401 AUTH_INVALID_CREDENTIALS "email 또는 비밀번호가 맞지 않습니다"
     400 VALIDATION_ERROR

POST /api/v1/auth/logout
성공 204, session 쿠키 삭제(발급 때와 같은 속성). 쿠키가 없어도 204

GET /api/v1/auth/me
성공 200 { "id", "email", "display_name", "is_demo" }
실패 401 AUTH_REQUIRED

오류 본문: { "error": { "code", "message", "details", "request_id" } }
```

- **데이터**: `users`(`id` UUID PK DEFAULT `gen_random_uuid()`, `email` VARCHAR(254) NOT NULL UNIQUE 소문자, `password_hash` TEXT NOT NULL, `display_name` VARCHAR(50) NOT NULL, `is_demo` BOOLEAN NOT NULL DEFAULT false, `created_at` TIMESTAMPTZ NOT NULL DEFAULT now())
- **비밀번호**: `bcrypt>=5,<6`, cost 12. 더미 해시도 같은 cost로 기동 시 한 번 만든다.
- **토큰**: `PyJWT>=2.10,<3`, HS256 고정, `exp`·`iat`·`sub` 필수. 서명 키는 `AUTH_SECRET`만 쓴다.
- **환경변수**: `AUTH_SECRET`(필수, 32바이트 이상, RFC 7518 §3.2), `COOKIE_SECURE`(기본 켜짐, 정확히 `0`일 때만 끔. 오타가 나도 안전한 쪽으로 남는다)
- **구조**: 라우터·의존성·저장소는 `backend/auth.py`, `backend/main.py`는 연결만. `UserRepository` Protocol을 `get_user_repository` 의존성으로 주입해 테스트는 가짜 저장소로 override한다.
- **제약**: JWT는 서버가 상태를 갖지 않는다. 로그아웃은 브라우저의 쿠키를 지울 뿐이므로, 그 전에 복사된 토큰은 `exp`까지 유효하다. 폐기 목록은 범위 밖이다.
- **오류 코드**: 정본은 SPEC.md §6 "오류 코드" 표다. `AUTH_INVALID_CREDENTIALS`, `AUTH_REQUIRED`, `VALIDATION_ERROR`는 SDD §7.7을 따른다. `INTERNAL_ERROR`(500)는 SDD에 없어 새로 정한 코드다.

## AC (Given-When-Then)

**AC-AUTH-01 · 로그인 성공과 쿠키 속성**
- GIVEN: 시드된 계정
- WHEN: 맞는 email·password로 로그인
- THEN: 204, 빈 본문, `Set-Cookie`에 `HttpOnly; Max-Age=28800; Path=/; SameSite=Lax; Secure`

**AC-019 · 계정 존재 여부를 숨김**
- GIVEN: 시드된 계정 하나
- WHEN: 틀린 비밀번호로, 또 없는 이메일로 로그인
- THEN: 둘 다 401 `AUTH_INVALID_CREDENTIALS`, 메시지 "email 또는 비밀번호가 맞지 않습니다", `request_id`를 뺀 본문이 동일, 두 경우 모두 해시 비교 1회

**AC-020 · 비밀번호 비노출**
- GIVEN: 식별 가능한 비밀번호 문자열
- WHEN: 로그인 성공·실패·400을 일으킴
- THEN: 응답 본문·헤더와 로그 어디에도 그 문자열이 없다

**AC-AUTH-02 · 세션 검증**
- GIVEN: 쿠키 없음, 다른 키로 서명한 토큰, `alg=none` 토큰, 만료 토큰 중 하나
- WHEN: `GET /api/v1/auth/me`
- THEN: 401 `AUTH_REQUIRED`, 공통 오류 형식

**AC-AUTH-03 · 로그아웃**
- GIVEN: 로그인된 클라이언트
- WHEN: 로그아웃 후 `/me` 호출
- THEN: 로그아웃 204, `/me` 401

**AC-AUTH-04 · me 응답**
- GIVEN: 로그인된 클라이언트
- WHEN: `GET /api/v1/auth/me`
- THEN: 200, 키가 정확히 `id`, `email`, `display_name`, `is_demo`(`password_hash` 없음)

**AC-AUTH-05 · 기동 검증**
- GIVEN: `AUTH_SECRET`이 없거나 32바이트 미만
- WHEN: 앱 기동
- THEN: `AUTH_SECRET`을 언급한 오류로 기동 실패

**AC-AUTH-06 · Secure 끄기**
- GIVEN: `COOKIE_SECURE=0`
- WHEN: 로그인
- THEN: 쿠키에 `Secure`가 없다. 변수가 없거나 다른 값이면 `Secure`가 있다
