# 기업명 영문·한글 별칭 검색

## Why

- 심사역이 `KCTC`, `NPC`, `엘지화학`처럼 익숙한 표기를 입력해도 현재 보유 기업 검색과 심사 건 생성에서 회사를 찾지 못한다.
- 두 화면의 검색 원천이 달라 한쪽만 고치면 검색 결과와 심사 대상이 어긋난다.
- 측정 지표: 등록된 별칭의 2페이지 검색 및 3페이지 심사 건 대상 식별 성공률 100%.

## Goal

- 활성 100개 기업을 살펴 명확한 영문 약칭과 한글 표기만 `corp_code`별로 등록한다.
- 2·3페이지의 기업명 표시는 공시 회사명 그대로 유지하고, 별칭은 검색에만 사용한다.
- 3페이지는 같은 별칭을 실제 연도별 `documents` 행의 `corp_code`로 해석한다.
- 범위 밖: 임의 로마자 변환, 발음 유사도·오타 검색, 코퍼스 기업명 변경, 새 기업·새 연도 데이터 추가.

## What

- `data/company_aliases.json`을 한 곳의 수동 검증 별칭 목록으로 둔다. 기존 manifest의 `corp_name`은 표시·검색의 기본값이다.
- 공백·대소문자·전각 영숫자를 정규화해 회사명, 별칭, 8자리 고유번호를 찾는다.
- 정확히 일치하는 기업이 하나면 선택한다. `엘지`처럼 부분 검색 결과가 여럿이면 고유번호가 붙은 후보를 보여주고 사용자가 고르게 한다.
- 별칭이 있어도 선택한 사업연도의 문서가 없으면 심사 건을 만들지 않는다. 새 연도에는 같은 고유번호의 별칭을 재사용한다.

## How

- 첫 화면 데이터 생성기는 서비스 manifest와 별칭 목록을 합쳐 `landing-data.js`를 만든다. 별칭을 추가해도 기업 수는 늘지 않는다.
- 서버는 같은 JSON을 읽어 `documents`의 회사 목록과 대조한다. 클라이언트가 보낸 회사명이나 별칭을 고유번호로 확정한 뒤 기존 생성 흐름을 사용한다.
- 후보 오류에는 회사명·고유번호만 넣는다. 사용자의 검색어, 내부 설정, 문서 본문은 응답에 담지 않는다.
- 별칭은 확인 가능한 영문 약칭과 흔한 한글 표기만 등록한다. `엘쥐` 등 추측 가능한 발음 변형을 무제한 생성하지 않는다.

## AC (Given-When-Then)

- GIVEN 케이씨티시(00103042), WHEN `kctc`를 입력, THEN 2페이지에서 `케이씨티시` 카드가 보이고 3페이지에서 해당 고유번호로 심사 건이 생성된다.
- GIVEN 엔피씨(00108038), WHEN `NPC`를 입력, THEN 두 화면에서 같은 기업을 찾는다.
- GIVEN NAVER(00266961), WHEN `네이버`를 입력, THEN 두 화면에서 `NAVER`를 찾는다.
- GIVEN 이월드(00540605), WHEN `e-world`를 입력, THEN 두 화면에서 `이월드`를 찾는다.
- GIVEN LG화학(00356361), WHEN `엘지화학`을 입력, THEN LG화학을 찾는다. WHEN `엘지`만 입력, THEN LG 계열사 후보를 보여준다.
- GIVEN 별칭에 해당하는 기업의 선택 연도 문서가 없음, WHEN 생성 요청, THEN 422를 반환한다.
- GIVEN 새 기업을 manifest에 추가, WHEN 첫 화면 데이터를 다시 생성, THEN 기업 수만 늘고 기존 고유번호·별칭 연결은 유지된다.
