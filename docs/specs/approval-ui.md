# Spec - Approval UI (판정 초안 승인·수정·취소 화면)

심사 건 상세·질의 화면(review-detail-ui, PR #85) 다음 작업. 계약 근거: SPEC.md §3.1~3.3(항목·판정·응답), §3.5(상태 전이), §5.5(승인과 저장), §6(API 목록·오류 본문). `/approvals`, `/approvals:cancel`의 요청·응답 상세는 SDD §9를 따르지만 이 저장소에는 없어 아래 "응답 형태(제안)"으로 먼저 만든다.

> 이 Spec은 `feat/review-detail-ui` 위에 쌓는다. PR #85가 병합되면 `main` 기준으로 맞춘다.

## Why

- **페르소나**: 기업여신 심사역. 모델이 만든 항목별 판정 초안을 검토하고, 틀린 것은 고치고, 확정한 것만 심사 메모로 남긴다.
- **상황**: 질의 결과가 `awaiting_approval`이 되면 지금 화면은 "승인 화면은 준비 중입니다"만 보이고 질문도 막힌다. 심사 건은 이 상태에서 빠져나올 수 없다.
- **문제**:
  1. 승인 없이는 메모가 저장되지 않아 제품의 마지막 단계(사람이 확정한 메모)를 볼 수 없다.
  2. 심사역이 고친 항목만 규칙으로 쌓이는 구조(SPEC §5.5)라서, 어떤 항목을 고쳤는지가 화면에서 분명해야 한다.
  3. 승인하지 않고 초안을 버릴 방법(취소)이 없다.
  4. 백엔드(`/approvals`)가 아직 `main`에 없어 계약만 보고 먼저 만든다.
- **측정 지표**: 승인·수정 후 승인·취소 흐름을 자동화 테스트와 브라우저(가짜 응답)에서 각 1회 이상 확인. 화면에 승인자 값을 보내거나 보이는 경로 0건, 서버 오류 세부 정보 노출 0건.

## Goal

- **해결 목표**: `status=awaiting_approval`인 심사 건에서 사용자가 판정 초안을 검토·수정해 승인하거나, 승인하지 않고 취소한다.
- **성공 기준**:
  1. 승인 대기 심사 건에서 항목별 판정 초안을 편집 가능한 형태로 보인다.
  2. 판정(verdict)과 이유(reason)를 항목마다 고칠 수 있고, 고친 항목은 "수정됨"으로 표시된다.
  3. 「승인」은 `approvals`를, 「취소」는 `approvals:cancel`을 한 번만 호출하고, 성공하면 심사 건을 다시 불러와 `open`으로 돌아온 상태를 보인다.
  4. 중복 승인(409)·세션 만료(401)·없는 건(404)을 각각 정해진 방식으로 처리한다.
  5. 이 화면의 자동화 테스트가 통과한다.
- **Out of Scope**: 승인자 선택·표시(서버가 세션 user_id로 정한다), 규칙 저장·관리(서버 `save_memo` 몫, 규칙 화면은 별도), 메모 되돌리기, 인용 원문 전체 보기, 항목 추가·삭제, 인용 편집, 심사 종료, 백엔드 구현.

## What

### Happy Path

1. 심사 건이 `awaiting_approval`이다(질의 직후이거나 다시 연 화면).
2. 화면이 항목별 초안(항목 이름, 판정, 이유, 인용)을 편집 폼으로 보인다. 인용은 읽기 전용이다.
3. 사용자가 판정 라디오(해당/비해당/확인필요)와 이유 텍스트를 고친다. 고친 항목에는 「수정됨」 표시가 붙는다.
4. 「승인」을 누르면 확인 문구 후 `POST /api/v1/reviews/{id}/approvals`를 보낸다. 요청 중에는 버튼을 막고 「저장 중…」을 보인다.
5. 200이면 심사 건을 다시 불러 `status=open`, 「심사 메모로 저장했습니다」를 보이고 질문 입력이 다시 열린다.

### Edge Cases

| # | 상황 | 처리 방식 |
|---|---|---|
| EC-01 | 아무것도 고치지 않고 승인 | 허용한다. 요청의 모든 항목은 원본과 같고 「수정됨」 0건. 규칙 저장 여부는 서버가 정한다. |
| EC-02 | 이유를 비우거나 1000자 초과 | 요청을 보내지 않고 해당 항목 아래 「이유를 1~1000자로 입력하세요」를 보인다. |
| EC-03 | 판정을 `needs_check`가 아닌 값으로 고쳤는데 인용 검증이 실패(`passed=false`)인 항목 | 요청을 막지 않는다(서버가 판단). 항목에 「검증 실패 인용 있음」 경고를 보인다. SPEC §5.4가 서버에서 최종 검사한다. |
| EC-04 | 알 수 없는 `item`·`verdict` | 「알 수 없음」으로 보이고, 알 수 없는 판정값은 그대로 되돌려 보낸다(고치지 않았다면 원본 유지). 라디오에는 없으므로 선택 상태 없음. |
| EC-05 | 승인·취소 요청 중 재클릭 | 두 버튼 모두 비활성화한다. 요청은 한 번만 나간다. |
| EC-06 | 409 `CONFLICT_NOT_AWAITING_APPROVAL` | 「이미 처리된 승인입니다. 화면을 새로 불러옵니다」 후 심사 건을 다시 불러온다. |
| EC-07 | 401 | 로그인 화면(`/`)으로 이동한다. |
| EC-08 | 404 | 「심사 건을 찾을 수 없습니다」와 목록 링크. |
| EC-09 | 400 `VALIDATION_ERROR` | 「입력 내용을 확인해 주세요」. 서버 `details`는 보이지 않는다. 편집 내용은 유지한다. |
| EC-10 | 429·5xx·네트워크 단절·그 밖의 응답 | 상세 화면과 같은 문구. 편집 내용과 버튼 상태를 유지하고 다시 시도할 수 있다. |
| EC-11 | 취소 | 확인 문구 후 `approvals:cancel`. 성공하면 심사 건을 다시 불러 `open`으로 돌아오고 「초안을 취소했습니다. 저장된 메모는 없습니다」를 보인다. |
| EC-12 | 승인 성공 후 심사 건 재조회 실패 | 승인은 이미 된 것이므로 「저장했습니다. 상태를 새로 불러오지 못했습니다」와 「다시 불러오기」를 보인다. 승인을 다시 보내지 않는다. |
| EC-13 | 초안·이유·회사명에 `<`, `&` | 글자 그대로 보인다(`textContent`/`value`로만 넣는다). |
| EC-14 | 화면을 다시 열었는데 `awaiting_approval`이고 초안이 응답에 없음 | 「승인할 초안을 불러오지 못했습니다」와 「취소」만 보인다. 승인은 막는다. (아래 계약 가정 ① 참고) |
| EC-15 | 상태가 `awaiting_approval`이 아님 | 승인 영역을 숨긴다. |

## How

- **화면 위치**: 새 경로 없이 `/reviews/{id}` 안에서 `awaiting_approval`일 때 결과 영역 아래 「승인 패널」을 보인다. 템플릿은 `review_detail.html`에 패널 구획을 더한다.
- **정적 자산**: `review-detail.js`에 승인 흐름을 더하거나(약 450줄 이상 커지면) `approval-panel.js`로 분리해 `createApprovalPanel({document, fetch, ...})` 팩토리를 `createReviewDetailController`가 쓴다. CSS는 `review-detail.css`를 확장한다. 파일 구성은 구현 때 줄 수를 보고 정한다.
- **계약 가정 (백엔드 담당 확인 필요)**
  - ① `GET /api/v1/reviews/{id}`는 `status=awaiting_approval`일 때 대기 중인 초안을 `pending_draft`(질의 응답의 `draft[]`와 같은 형태)로 포함한다. 없으면 화면은 질의 직후에만 승인할 수 있고, 새로고침 후에는 EC-14로 떨어진다.
  - 같은 체크포인트의 질문을 `pending_question`으로 받아 「심사 건 상세」 제목 아래, 기업 정보 위의 독립 카드 「내가 한 질문」에 표시한다. 질문 값이 없는 과거 데이터에서는 이 영역을 숨긴다. 상세 화면에서 방금 제출한 질문은 재조회 결과를 받기 전에도 표시한다.
  - 같은 초안을 작성할 때 참고한 `pending_applied_rules`가 있으면 「초안 승인」의 판정 목록 위에 「이번 초안에 참고한 내 규칙」으로 표시한다. 화면 이동이나 새로고침 뒤에도 같은 목록을 복원하며, 추가 질문의 참고 규칙은 해당 답변에 표시한다.
  - 「판정 기준」에서 해당·비해당·확인 필요의 뜻과 소송 예시를 안내한다.
  - 판정이나 이유를 수정한 항목에 「수정 내용 보기」를 표시한다. 펼치면 처음 표시한 AI 초안과 현재 입력한 판정·이유가 보인다. 원래 값으로 되돌리면 비교 영역을 숨긴다.
  - ② `POST /api/v1/reviews/{id}/approvals`, body `{"decisions": [{"item": string, "verdict": string, "reason": string}]}`. 원본 초안의 모든 항목을 같은 순서로 보낸다. **승인자(`approved_by`)는 보내지 않는다**(서버가 세션 user_id로 정한다). 고친 항목 판단은 서버가 원본과 비교해 한다.
  - ③ 200 응답 본문은 `{"review_id", "approval_seq", "memo_id"}` 정도로 보지만 화면은 파싱하지 않고, 성공 뒤 `GET /reviews/{id}`를 다시 부른다.
  - ④ `POST /api/v1/reviews/{id}/approvals:cancel`, body 없음, 200 또는 204.
  - ⑤ 오류: 409 `CONFLICT_NOT_AWAITING_APPROVAL`(SPEC §5.5), 400 `VALIDATION_ERROR`, 401, 404, 429. 화면은 HTTP 상태로만 분기하고 서버 본문은 쓰지 않는다.
  - 위 형태가 바뀌면 이 Spec과 JS의 요청 조립만 고친다.
- **수정 판단**: 화면의 「수정됨」은 원본 초안과 비교한 표시용이다(`verdict` 또는 `reason`이 다름). 서버가 규칙 저장 여부를 정하는 것과 별개다.
- **보안 제약**: 서버 문자열은 `textContent`/`value`로만 넣고 `innerHTML`은 쓰지 않는다. `approved_by`·사용자 ID·`request_id`·서버 오류 본문을 요청하거나 출력하지 않는다. 같은 출처 `fetch`와 `credentials: "same-origin"`만 쓴다. 승인·취소는 요청 한 번에 재시도 루프를 두지 않는다(수동 재시도만).
- **디자인**: 기존 토큰·글래스 패널·pill 버튼·모노 라벨을 쓴다. 수정됨 표시는 색만으로 구분하지 않고 글자 라벨을 함께 보인다. 라디오·텍스트 영역·버튼 높이 ≥ 2.75rem. 승인은 주 버튼, 취소는 보조 버튼. 320px에서 가로 스크롤이 없다.
- **변경 파일 범위**: `backend/templates/review_detail.html`, `backend/static/review-detail.{js,css}`(필요 시 `approval-panel.js`), `tests/review_detail_web_ui.test.mjs`, `tests/test_review_detail_web_ui.py`, 승인 전용 테스트 파일 `tests/approval_web_ui.test.mjs`, 이 Spec. `backend/main.py`는 바꾸지 않는다.

## AC (Given-When-Then)

**AC-01 · 승인 패널 표시**
- GIVEN: 심사 건 `status=awaiting_approval`, 초안 2개
- WHEN: 화면이 열리거나 질의 응답이 `awaiting_approval`
- THEN: 항목마다 이름·판정 라디오 3개·이유 입력·읽기 전용 인용이 보이고, 「승인」「취소」 버튼이 있다. 「준비 중」 문구는 사라진다. 질문 입력은 막혀 있다.

**AC-02 · 수정 표시**
- GIVEN: 승인 패널
- WHEN: 판정이나 이유를 원본과 다르게 바꿈 / 원래대로 되돌림
- THEN: 해당 항목에 「수정됨」 글자 라벨이 생김 / 사라짐. 고친 개수가 요약에 보인다.

**AC-03 · 승인 요청**
- GIVEN: 항목 2개 중 1개를 고침
- WHEN: 「승인」 확인
- THEN: `POST /api/v1/reviews/{id}/approvals` 본문은 `{decisions:[{item,verdict,reason}×2]}`이고 `approved_by`·사용자 ID 필드가 없다. 요청 중 두 버튼이 비활성화되고 「저장 중…」이 보인다. 요청은 정확히 1회다.

**AC-04 · 승인 성공**
- GIVEN: 승인 200
- WHEN: 응답을 받음
- THEN: 심사 건을 다시 불러 `status=open`이면 승인 패널이 사라지고 「심사 메모로 저장했습니다」와 질문 입력이 열린다. 재조회 실패면 EC-12 문구와 「다시 불러오기」를 보이고 승인은 다시 보내지 않는다.

**AC-05 · 취소**
- GIVEN: 승인 패널
- WHEN: 「취소」 확인
- THEN: `POST .../approvals:cancel`이 1회 나가고 성공하면 심사 건을 다시 불러 `open`으로 돌아오며 EC-11 문구를 보인다. 확인을 거절하면 요청이 나가지 않는다.

**AC-06 · 입력 선검증**
- GIVEN: 이유가 비었거나 1000자 초과인 항목
- WHEN: 「승인」
- THEN: 요청을 보내지 않고 해당 항목에 안내 문구를 보인다.

**AC-07 · 중복 승인**
- GIVEN: 승인 응답 409
- WHEN: 응답을 받음
- THEN: EC-06 문구 후 심사 건을 다시 불러온다. 승인을 자동 재전송하지 않는다.

**AC-08 · 세션 만료와 없는 건**
- GIVEN: 승인·취소 응답 401 / 404
- WHEN: 응답을 받음
- THEN: 401은 `/`로 이동, 404는 안내 문구와 목록 링크.

**AC-09 · 오류 구분과 편집 유지**
- GIVEN: 승인·취소에서 fetch 예외, 5xx, 429, 400, 그 밖의 응답
- WHEN: 응답을 받음
- THEN: EC-09·10의 문구를 보이고 버튼을 다시 활성화하며 편집 내용은 유지한다. 서버 `details`·`request_id`는 보이지 않는다.

**AC-10 · 초안 없음**
- GIVEN: `awaiting_approval`인데 `pending_draft`가 없음(재진입)
- WHEN: 화면이 열림
- THEN: EC-14 문구와 「취소」만 보이고 승인 버튼은 없다.

**AC-11 · HTML 비해석·알 수 없는 값**
- GIVEN: 이유·항목·회사명이 `<img src=x onerror=alert(1)>`, 알 수 없는 `item`·`verdict`
- WHEN: 표시·편집
- THEN: 글자 그대로 텍스트로 보이고 요소로 만들어지지 않는다. 알 수 없는 값은 「알 수 없음」이며 화면이 깨지지 않는다.

**AC-12 · 스타일·접근성**
- GIVEN: 화면 CSS·마크업
- WHEN: 검사
- THEN: 라디오는 `fieldset`/`legend`로 묶이고 모든 입력에 라벨이 있다. 오류는 `role="alert"`로 알린다. 대화형 요소 높이 ≥ 2.75rem, `prefers-reduced-motion`을 따른다. 320~1280px에서 가로 스크롤이 없다(브라우저 확인).

**AC-13 · 비밀·외부 리소스·범위**
- GIVEN: 이 화면의 HTML·CSS·JS
- WHEN: 검사
- THEN: 외부 URL·`innerHTML`·`eval`·비밀값이 없고 LLM 호출 코드가 없다. `rules`·`memos`·`chunks` 엔드포인트를 호출하지 않는다.
