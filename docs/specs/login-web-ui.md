# Spec - Login Web UI

## Why

- **페르소나**: 기업여신 심사역이 웹 브라우저에서 서비스에 처음 접속한다.
- **상황**: 이미 구현된 인증 API로 로그인해야 이후 심사 건과 질의 기능을 사용할 수 있다.
- **문제**: 현재 인증 API는 있으나 브라우저에서 사용할 화면, 성공·실패 피드백, 현재 세션 상태를 확인할 방법이 없다.
- **측정 지표**: 데모 계정으로 로그인하면 심사 건 화면(`/reviews`)으로 바로 이동하고, 로그아웃 뒤 보호 화면에 남지 않는 흐름을 브라우저와 자동화 테스트에서 각각 1회 이상 확인한다.

## Goal

- **해결 목표**: 같은 출처의 서버 렌더링 로그인 화면을 제공하고 기존 인증 API와 연결한다.
- **성공 기준**:
  1. `POST /api/v1/auth/login` 성공(204) 뒤 `GET /api/v1/auth/me`로 세션을 확인하고 `/reviews`로 이동한다. 사용자 이름은 그 화면에서 보여 준다.
  2. 실패(401) 때 서버 오류 전문이나 계정 존재 여부를 노출하지 않고 정해진 로그인 실패 문구만 표시한다.
  3. 로그아웃은 `/reviews`에서 하며(reviews-web-ui AC-13), 뒤에 `GET /api/v1/auth/me`가 401이 되어 로그인 화면으로 돌아온다.
  4. 로그인 관련 화면·정적 자산·라우트의 자동화 테스트가 통과한다.
- **Out of Scope**: 회원 가입, 비밀번호 재설정, SSO, 심사 건·질의·승인 UI, 디자인 시스템 도입, 인증 API 계약 변경.

### 사용성 보완(feat/login-usability) 추가 목표

실제 브라우저 확인에서 드러난 빈틈을 메운다. 인증 API 계약, 비밀번호·토큰 보관 금지 제약은 그대로다.

- 어떤 화면 상태에서도 오류 문구가 사용자에게 보인다.
- 요청 중·확인 중 상태가 눈에 보이고, 첫 화면에서 폼이 깜빡이지 않는다.
- 실패 뒤 키보드·스크린리더 사용자가 다음 행동(비밀번호 재입력)으로 바로 이어진다.

### 로그인 이동(feat/login-redirect-reviews) 변경 목표

로그인 뒤 심사 건 화면까지 한 번에 이어지게 한다. 인증 API 계약은 그대로다.

- 로그인에 성공하면 링크를 누르지 않아도 `/reviews`로 이동한다.
- 이미 로그인한 채 `/`에 오면 첫 화면에 머물며 로그인 버튼을 숨기고 「심사 건 확인」으로 `/reviews`에 갈 수 있다([첫 화면 이동 스펙](home-review-navigation.md)).
- 로그인 폼은 비로그인 사용자 전용이다. "로그인되었습니다" 영역과 로그아웃 버튼은 없다.

## What

### Happy Path

1. 비로그인 사용자가 `/`에 접속하면 로그인 화면을 본다.
2. 사용자가 이메일과 비밀번호를 입력하고 제출한다.
3. 브라우저가 `POST /api/v1/auth/login`에 JSON을 전송한다.
4. 성공 시 브라우저가 HTTP-only 세션 쿠키를 자동으로 보관하고 `/api/v1/auth/me`를 호출한다.
5. 세션이 확인되면(`/me` 200) 화면은 `/reviews`로 이동한다.
6. 로그아웃은 `/reviews`의 버튼이 `POST /api/v1/auth/logout`을 호출한 뒤 `/`로 이동해서 한다(reviews-web-ui AC-13).

### Edge Cases

| # | 상황 | 처리 방식 |
|---|---|---|
| EC-01 | 이메일 또는 비밀번호가 틀림 | `AUTH_INVALID_CREDENTIALS`에만 공통 실패 문구를 보이고 입력 비밀번호는 지운다. |
| EC-02 | 네트워크 또는 5xx 오류 | 계정 정보와 무관한 오류 문구를 보이고 같은 폼으로 다시 제출할 수 있다. 네트워크 단절과 서버 오류는 문구를 구분한다(AC-11). |
| EC-03 | 로그인된 채 `/`에 접속하거나 새로 고침 | 첫 `/api/v1/auth/me`가 200이면 첫 화면에 머물며 로그인 버튼을 숨긴다(AC-05). |
| EC-04 | 세션이 만료되거나 없음 | `/api/v1/auth/me`의 401을 로그인 상태가 아님으로 처리한다. |
| EC-05 | 제출을 연속으로 누름 | 요청 중에는 제출 버튼을 비활성화해 중복 로그인을 막는다. |
| EC-06 | 로그아웃 요청이 실패 | (이전) 로그아웃은 `/reviews`에서 한다. 실패 처리는 reviews-web-ui EC·AC-13이 맡는다. |
| EC-07 | 로그인이 204인데 곧바로 `/me`가 401 | 쿠키가 저장되지 않은 것으로 보고 세션 미보관 안내를 보인다(AC-10). |
| EC-08 | 첫 `/me` 응답 전 | 로그인 폼은 보이지 않고 확인 중 표시만 보인다(AC-08). |
| EC-09 | 로그아웃 실패 뒤 재시도해 성공 | (이전) 성공하면 `/`로 이동하므로 남는 문구가 없다. 이 화면에는 로그아웃이 없다. |
| EC-10 | 로그인 시도가 429·403 같은 4xx로 실패 | 세션 확인 문구가 아니라 로그인 시도에 맞는 문구를 보인다(AC-14). |

## How

- **화면 경로**: `GET /`는 Jinja2 템플릿 `backend/templates/login.html`을 반환한다. 로그인 제출 뒤 세션이 확인되면 컨트롤러에 주입한 `navigate("/reviews")`(실제로는 `window.location.assign`)로 이동한다. 최초 세션 확인에서는 첫 화면에 머문다.
- **정적 자산**: `backend/static/login.css`, `backend/static/login.js`를 같은 FastAPI 앱에서 `/static`으로 제공한다.
- **API 사용**:
  - 로그인: `POST /api/v1/auth/login`, body `{"email": string, "password": string}`, 성공 204.
  - 현재 사용자: `GET /api/v1/auth/me`, 성공 200의 `id`, `email`, `display_name`, `is_demo`만 사용.
  - 로그아웃: 이 화면에서는 호출하지 않는다. `/reviews`가 `POST /api/v1/auth/logout`을 호출한다.
- **보안 제약**:
  - 비밀번호·세션 토큰을 JavaScript 변수, `localStorage`, `sessionStorage`, 로그, DOM에 보관하지 않는다.
  - `fetch`는 같은 출처 요청으로만 하고 서버가 발급한 HTTP-only 쿠키를 이용한다.
  - 실패 화면은 서버 오류의 `details`·`request_id`를 출력하지 않는다.
- **의존성**: 서버 렌더링을 위해 `backend/requirements.txt`에 `jinja2`를 추가한다. FastAPI·바닐라 JavaScript 외 프런트엔드 프레임워크는 추가하지 않는다.
- **변경 파일 범위**: `backend/main.py`, `backend/requirements.txt`, `backend/templates/login.html`, `backend/static/login.css`, `backend/static/login.js`, `backend/templates/reviews.html`, `backend/static/reviews.js`, `tests/test_login_web_ui.py`, `tests/test_reviews_web_ui.py`, `tests/login_web_ui.test.mjs`, `tests/reviews_web_ui.test.mjs`, 이 Spec과 reviews-web-ui Spec.
- **사용성 보완의 구현 제약**:
  - 오류 영역(`#login-error`)은 `role="alert"`를 쓰고 `<form>` 밖에 둔다. 폼이 숨겨져도 보여야 하기 때문이다.
  - 첫 화면의 폼은 `hidden`으로 시작하고 `#login-status`(확인 중 표시)를 보인다. JavaScript가 꺼진 경우를 위해 `<noscript>` 안내를 둔다.
  - 이동하는 동안에는 폼을 숨긴 채 `#login-status`의 글자를 「심사 건 화면으로 이동하는 중…」으로 바꿔 보인다(빈 화면과 폼 깜빡임을 막는다).
  - 문구는 다음 일곱 가지로 고정한다. 입력값, 서버의 `details`·`request_id`는 넣지 않는다.
    - 로그인 실패(401): 「이메일 또는 비밀번호가 맞지 않습니다.」
    - 네트워크 단절(fetch 예외): 「서버에 연결할 수 없습니다. 네트워크를 확인하고 다시 시도해 주세요.」
    - 서버 오류(5xx): 「서버에 문제가 있어 로그인할 수 없습니다. 잠시 후 다시 시도해 주세요.」
    - 세션 미보관(204 뒤 `/me` 401): 「로그인은 되었지만 세션을 유지하지 못했습니다. 브라우저의 쿠키 설정을 확인하고 다시 시도해 주세요.」
    - 로그인 시도가 429: 「로그인 시도가 너무 많습니다. 잠시 후 다시 시도해 주세요.」
    - 로그인 시도가 그 밖의 4xx(400·403·404 등): 「로그인하지 못했습니다. 입력을 확인한 뒤 다시 시도해 주세요.」
    - 첫 세션 확인(`/me`)이 401·5xx가 아닌 이상 응답: 「로그인 상태를 확인할 수 없습니다. 잠시 후 다시 시도해 주세요.」
  - 비밀번호 표시 버튼은 `aria-controls="password"`로 입력 칸과 연결하고, 상태는 글자(「표시」↔「숨김」)로만 알린다(`aria-pressed`를 함께 쓰면 스크린리더가 상태를 중복해 읽는다). 사용자가 누를 때만 `type`을 바꾸고, 요청이 끝나면 다시 `password`로 되돌린다. 값을 다른 곳에 저장하지 않는다.
  - 좁은 화면(폭 360px)에서 가로 스크롤 없이 폼이 보이도록 위아래 여백을 줄이고 좌우 여백 1rem을 둔다. 이 항목은 자동화 테스트 대신 브라우저에서 확인한다.

## AC (Given-When-Then)

**AC-01 · 로그인 화면 제공**
- GIVEN: 비로그인 브라우저
- WHEN: `GET /` 요청
- THEN: 이메일·비밀번호 입력과 제출 버튼을 포함한 HTML을 200으로 받는다. 이 화면에는 로그아웃 버튼과 "로그인되었습니다" 영역이 없다.

**AC-02 · 로그인 성공 후 이동**
- GIVEN: 유효한 데모 계정
- WHEN: 로그인 폼을 제출하고 로그인 API가 204, 이어지는 `/api/v1/auth/me`가 200
- THEN: `/reviews`로 이동하고, 비밀번호 입력값은 화면에 남지 않는다.

**AC-03 · 로그인 실패 정보 비노출**
- GIVEN: 틀린 비밀번호 또는 존재하지 않는 이메일
- WHEN: 로그인 API가 401을 반환
- THEN: 두 경우 모두 같은 사용자용 실패 문구만 보이고, API 오류 세부 정보는 표시하지 않는다.

**AC-04 · 로그아웃(이전)**
- 로그아웃은 `/reviews`에서 한다(reviews-web-ui AC-13). 이 화면은 로그아웃 뒤 `/`로 돌아온 사용자에게 로그인 폼을 보여 주는 것으로 이어진다(AC-05의 401 경로).

**AC-05 · 기존 세션이면 로그인 폼 생략**
- GIVEN: 유효한 세션 쿠키
- WHEN: `/`에 접속하거나 새로 고침
- THEN: 첫 `/api/v1/auth/me`가 200이면 첫 화면에 머물며 로그인 폼과 로그인 버튼을 숨긴다. 401이면 로그인 폼을 보인다.

**AC-06 · 로그아웃 실패 안내(이전)**
- 이 화면에는 로그아웃이 없다. 같은 요구는 reviews-web-ui AC-13이 맡는다.

**AC-07 · 요청 중 표시**
- GIVEN: 로그인 폼 제출 직후
- WHEN: 로그인 응답을 기다리는 동안
- THEN: 제출 버튼은 비활성화되고 글자가 「로그인 중…」이며, 응답이 끝나면 「로그인」으로 돌아온다.

**AC-08 · 첫 확인 중 깜빡임 방지**
- GIVEN: 페이지 최초 로드
- WHEN: 첫 `/api/v1/auth/me` 응답 전
- THEN: 로그인 폼은 숨겨지고 확인 중 표시만 보인다. 응답이 401이거나 오류면 확인 중 표시는 사라지고 폼(오류면 오류 문구도)이 보인다. 첫 세션 확인이 200이면 첫 화면에 머물며 로그인 버튼과 확인 중 표시를 숨긴다. 로그인 제출 후 200이면 「심사 건 화면으로 이동하는 중…」을 보이고 `/reviews`로 이동한다.

**AC-09 · 실패 뒤 입력 이어가기**
- GIVEN: 로그인 API가 401을 반환
- WHEN: 실패 문구가 표시됨
- THEN: 비밀번호 입력에 포커스가 가고, 오류 영역은 `role="alert"`로 즉시 읽힌다.

**AC-10 · 세션 미보관 안내**
- GIVEN: 로그인 API가 204를 반환
- WHEN: 이어지는 `/me`가 401
- THEN: 로그인 폼을 유지하고 세션 미보관 문구를 표시한다.

**AC-11 · 오류 종류별 문구**
- GIVEN: 로그인 요청
- WHEN: fetch가 예외를 던지면 네트워크 단절 문구, 5xx 응답이면 서버 오류 문구를 표시
- THEN: 두 경우 모두 입력한 이메일·비밀번호와 서버 오류 세부 정보를 문구에 넣지 않는다.

**AC-12 · 비밀번호 표시 전환**
- GIVEN: 비밀번호 입력이 가려진 상태
- WHEN: 「표시」 버튼을 누르면 입력이 보이고 버튼 글자가 「숨김」이 되며, 다시 누르거나 요청이 끝나면 가려지고 「표시」로 돌아온다
- THEN: 전환은 입력 칸의 `type`만 바꾸며 비밀번호 값을 다른 곳에 저장하지 않는다.

**AC-13 · 로그아웃 재시도 성공 시 오류 제거(폐지)**
- 로그아웃 성공은 `/`로의 이동이라 남는 문구가 없다. 이 화면에는 로그아웃이 없다.

**AC-14 · 로그인 시도 4xx 문구**
- GIVEN: 로그인 API가 401이 아닌 4xx를 반환
- WHEN: 응답을 받음
- THEN: 429면 「로그인 시도가 너무 많습니다…」, 그 밖의 4xx면 「로그인하지 못했습니다. 입력을 확인한 뒤…」를 보이고, 「로그인 상태를 확인할 수 없습니다」는 보이지 않는다. 401은 기존 로그인 실패 문구를 유지한다.
