# 그래프 40+1 검색 지연 원인 분석

## 측정 범위

- 원본: `evals/results/graph50/graph167_full_*`(일상어 23문항·동결 v2 50문항, 그래프 켬 49+1 대 40+1), 기계 판독 합계 `graph167_full_comparison.json`.
- 검색 시간은 `supervisor/retriever` 노드, 리랭커 시간은 각 `retrieval_calls[].rerank_latency_ms`를 사용한다. `검색 - 리랭커`는 임베딩·BM25·벡터 검색·그래프·주변 처리의 합계로, 임베딩만의 독립 시간은 아니다.
- p95는 오름차순 `ceil(0.95×n)`번째다. 일상어는 검색 노드 23개, 동결 v2는 실제 검색 노드가 실행된 34개를 센다.

| 지표 | 일상어 49+1 | 일상어 40+1 | 동결 v2 49+1 | 동결 v2 40+1 |
| --- | ---: | ---: | ---: | ---: |
| 리랭커 입력 글자(그래프 호출) | 1,049,089 | 864,036 | 1,612,699 | 1,323,354 |
| 리랭커 p95 | 1,253.5ms | 1,467.9ms | 3,083.7ms | 1,978.8ms |
| 리랭커 이외 검색 시간 p95 | 2,930.2ms | 2,436.0ms | 2,475.1ms | 2,374.8ms |
| 검색 노드 p95 | 3,854.0ms | 3,860.1ms | 4,051.2ms | 4,279.6ms |

두 구성요소 각각의 p95가 줄어도 **같은 문항에서 두 지연이 겹치면 합계 p95는 늘 수 있다.** 실제로 동결 v2 40+1의 p95를 결정하는 48번은 리랭커가 1,406.0→1,978.8ms로 흔들렸다. 25번은 리랭커가 1,638.8→1,592.6ms로 약간 빨라졌지만 나머지 검색 시간이 2,286.7→3,208.6ms로 늘었다. 두 질문은 저장 벡터를 쓰지 않고 새 임베딩을 요청한 사례다.

동결 v2에서 저장 벡터 사용은 각 조건 23회, 새 임베딩은 각 조건 12회다. 새 임베딩 질문의 일부는 근거 없음·주제 밖 문항이며, 25·48번도 여기에 속한다. 이 외부 호출이 검색 상위 지연에 기여한다. 일상어는 질의 벡터를 고정하지 않아 각 조건의 임베딩 호출이 23회였다. Voyage 리랭커 지연도 40+1에서 항상 짧아지지는 않았다.

## 키 없는 국소 재생

- `DocumentGraph.expand`를 167번의 58개 검색 호출에 대해 20회씩, 총 1,160회 재생했다. 모든 이웃 ID가 기록과 일치했다. 중앙값 **0.0052ms**, p95 **0.0148ms**, 최대 **0.0568ms**였다. 이웃 탐색 자체는 초 단위 지연의 원인이 아니다. 그래프 구축은 약 0.78초로 요청 처리 전에 수행된다.
- 가짜 임베더·리랭커로 실제 코퍼스의 25번 검색을 반복하면 첫 호출 116.2ms, 이후 9.0~10.6ms였다. 외부 임베딩·리랭커가 없는 국소 검색은 기록된 수초 지연보다 훨씬 짧았다. 가짜 벡터의 검색 품질은 측정하지 않았다.
- 고정된 실제 질의 벡터가 있는 동결 v2 관련 23문항에 대해 BM25·벡터 RRF의 **원천 후보 상한 50→40**을 키 없이 재생했다. 원래 상한 50의 후보 ID는 저장 기록과 23/23 일치했다. 상한 40으로 바꾸면 23/23에서 RRF 상위 40개의 순서 또는 구성이 달라지고, 3·7·36·60번은 그래프 출발점 상위 5개도 달라졌다. **이 변경은 품질 위험이 있어 적용하지 않았다.**
- 리랭커에 보내는 일반 후보를 40→30으로 더 줄이는 것도 안전하지 않다. 현재 기록의 RRF 31~40위에는 일상어 5문항과 동결 v2 3문항의 정답 청크가 있고, 실제 최종 인용도 각각 4문항에서 이 구간을 사용했다.

## 결론과 측정 개선

40+1은 외부 리랭커에 보내는 글자를 약 18% 줄였지만, **1차 RRF 후보 50개 생성과 질의 임베딩 호출은 그대로**다. 그래프 이웃 계산은 무시할 만큼 짧고, 외부 임베딩·리랭커 응답 시간의 변동이 p95를 흔드는 주된 요인으로 보인다. 임베딩 호출별 시간이 별도 기록되지 않아 그 몫을 정확히 분리하지는 못했다. 현재 자료만으로 새로운 코드 설정의 실제 속도 개선을 확정할 수 없다.

167번 일상어 비교는 기준 조건을 23문항 한 프로세스로, 새 조건을 최대 5문항씩 다섯 프로세스로 실행했다. BM25 색인과 연결의 재사용 조건이 달라 시간 비교에 혼선이 있다. 다음으로 준비한 168번 그래프 끔/켬 평가는 같은 5문항 묶음과 같은 실행 순서를 양쪽에 적용하도록 수정됐다. 이 **측정 방식 개선**은 키 없이 확인했으며 실제 API 실행은 별도 승인이 필요하다. 그래프 기본값은 계속 꺼져 있다.

## 이번 키 없는 개선

- `docs/specs/retrieval-api-latency-evidence.md`와 `evals/PREREGISTER.md`에 외부 호출 시간 기록을 먼저 정의했다.
- `backend/services/llm.py`의 성공한 OpenRouter 임베딩·Voyage 리랭커 사용량 항목에 정수 `latency_ms`를 추가했다. 호출 모델·재시도·타임아웃·응답·검색 순위는 변경하지 않았다. 이후 평가의 질문별 결과 파일에서 임베딩과 리랭커 지연을 직접 분리할 수 있다.
- 모의 API 시험 2건에서 먼저 예상대로 실패한 뒤 구현 후 통과했다. 관련 시험 **234개 통과**, `git diff --check` 통과. 저장된 32개 사용량 항목에 지연값을 가상 추가해도 비용 요약이 완전히 같음을 키 없이 확인했다.
- **현재 서비스 속도가 빨라졌다고 주장하지 않는다.** 관측을 정확히 한 뒤 외부 호출의 긴 꼬리를 줄이는 변경을 하나씩 실험해야 한다. 추가 API 사용은 별도 고지와 승인이 필요하다.
