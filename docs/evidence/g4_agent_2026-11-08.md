# G4 에이전트 증거 정리 (2026-11-08)

> **11/10 갱신**: 아래 라우팅 설명(코드 규칙 Supervisor, redraft 노드, 검색 에이전트 안 rewriter, requery 기본 꺼짐)은 11/8 구조다. 11/10 사전 등록 104~106번으로 Supervisor가 방문마다 LLM 1회로 다음 일을 고르고 코드 guard가 고치는 구조로 바뀌었고, redraft·rewriter·requery 플래그는 지웠다. 지금 구조와 측정은 [ARCHITECTURE](../ARCHITECTURE.md)와 [EVAL_REPORT 4-32](../../EVAL_REPORT.md)에 있다. 승인 3노드·체크포인트 재개·Store 격리는 바뀌지 않아 아래 증거가 그대로 유효하다.

**결론: Supervisor와 서브에이전트 2개(검색·작성)로 나뉘어 있고, supervisor가 입력에 따라 거절·검색·작성만 다시(redraft)로 길을 고른다. 사람 승인 interrupt와 프로세스 재시작 뒤 재개, HTTP 승인 API, 로그인 사용자별 Store 격리를 각각 실제 부품으로 확인했다.** 확인하지 못한 것은 맨 아래에 적었다.

## Store 격리 시연 (11/8)

운영과 같은 부품으로 돌렸다: LangGraph `PostgresStore` + 의미 검색 색인(OpenAI 3-small, `runtime.rule_index_config`), 승인 그래프의 `save_memo` 노드, 질문 첫머리의 `load_rules` 노드. 메모 행 저장만 가짜 함수로 바꿨다. DB는 빈 `pgvector/pgvector:pg16` 컨테이너(실행 뒤 삭제)다.

1. 사용자 A가 승인하면서 '단기차입금' 항목의 이유를 **고쳤다**. 고치지 않은 '소송' 항목은 규칙이 되지 않는다.
2. 사용자 B는 '배당' 항목을 고쳤다.
3. 같은 질문 "오뚜기의 2025년 말 연결 기준 단기차입금은 얼마인가요?"로 두 사용자의 `load_rules`를 돌렸다.

| | Store에 저장된 키 (namespace `("memories", user_id)`) | 질문에 붙은 `applied_rules` |
|---|---|---|
| A | `memo-…-a-1:단기차입금` | A의 단기차입금 규칙 1개 |
| B | `memo-…-b-1:배당` | B의 배당 규칙 1개 (A의 규칙은 없음) |

결과: `격리 확인: 통과`. user_id는 서버가 로그인 세션에서 정하고(SPEC §5.5) 요청 본문으로 받지 않는다.

**함께 발견한 한계**: 의미 검색에 유사도 하한이 없어서, 그 사용자의 규칙이 5개(`SEMANTIC_RULE_TOP_K`) 이하이면 질문과 상관없는 규칙도 모두 작성기 입력에 붙는다(B의 '배당' 규칙이 차입금 질문에 붙음). 다른 사용자에게 새지는 않지만, 규칙이 쌓이면 관련 없는 지침이 작성에 섞일 수 있다. EVAL_REPORT 11장 약점에 적었다.

재현:

```powershell
docker run -d --name store-demo -e POSTGRES_PASSWORD=postgres -p 55433:5432 pgvector/pgvector:pg16
docker exec store-demo psql -U postgres -c "CREATE EXTENSION IF NOT EXISTS vector"
$env:STORE_DEMO_DATABASE_URL = "postgresql://postgres:postgres@localhost:55433/postgres"
python -X utf8 scripts/demo_store_isolation.py   # OPENAI_API_KEY 필요(임베딩 몇 번)
docker rm -f store-demo
```

## 확인하지 못한 것

- **재검색 루프의 v2 50건 실측**: supervisor의 requery(75번)와 검색 에이전트 안 재작성(80번)은 dry-run 9건에서만 돌았다(방아쇠 7건 모두 재작성 2회·검색 3회 뒤 맞게 거절). 점수 이득 없이 지연만 늘어 기본 꺼짐이다. 기본 경로에서 재작성은 0회다. (11/10: 104번 구조에서 Supervisor 지시 재검색이 v2 50건 기본 경로에서 회차당 14~19회 돈다. 다만 좋아진 문항은 0이다.)
- **운영 화면에서 규칙이 실제로 쌓이는 경로**: 운영 계정으로 '이유를 고쳐 승인 → 다음 질문'을 돌려 Langfuse에서 작성기 입력의 규칙을 본 기록은 없다. 위 시연은 같은 노드 함수를 직접 부른 것이다.

## 승인 재개 다시 돌리기 (11/12 추가, 키 없음·약 1분)

평가자가 재현하지 못했다는 11/11 코멘트를 받고 절차를 적는다. 가짜 검색기·작성기를 쓰므로 API 키와 검색 산출물이 필요 없다. 필요한 것은 docker와 파이썬 환경(`pip install -r backend/requirements.txt`)뿐이다.

```bash
# 1. 일회용 Postgres (끝나면 지운다. 운영 DB는 쓰지 않는다: 스크립트가 CHECKPOINT_DATABASE_URL만 읽는다)
docker run -d --rm --name resume-demo-pg -e POSTGRES_PASSWORD=demo -e POSTGRES_DB=demo -p 127.0.0.1:55439:5432 postgres:17
export CHECKPOINT_DATABASE_URL="postgresql://postgres:demo@127.0.0.1:55439/demo"

# 2. 단계마다 새 프로세스(pid가 달라진다)
python -X utf8 scripts/approval_resume_demo.py --step pause  --review-id demo-1 --graph multi   # 승인 대기로 멈춤
python -X utf8 scripts/approval_resume_demo.py --step resume --review-id demo-1 --graph multi   # 다른 프로세스에서 재개 → 메모 저장
python -X utf8 scripts/approval_resume_demo.py --step resume --review-id demo-1 --graph multi   # 같은 승인 재전송 → CONFLICT
python -X utf8 scripts/approval_resume_demo.py --step count  --review-id demo-1                 # 메모 1건

# 3. 정리
docker rm -f resume-demo-pg
```

볼 것: `pause`와 `resume`의 `pid`가 다르고, `resume`의 `calls_in_this_process`가 검색 0·작성 0이며(체크포인트에서 이어 감), 세 번째 실행이 `CONFLICT_NOT_AWAITING_APPROVAL`, `count`가 1이다. `--graph single`로 바꾸면 단일 그래프다. 11/12 실행 출력은 [d5_approval_resume_2026-11-11.jsonl](d5_approval_resume_2026-11-11.jsonl)에 그대로 있다.
