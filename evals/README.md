# 평가셋

G5: 최종 평가셋은 **50건 이상**(동결 시점 기준)이고 **관련 질문과 비관련 질문이 각각 절반**입니다. 개선 전후를 같은 셋으로 두 번 이상 재서 회귀를 숫자로 보입니다.

**평가셋이 쉬우면 어떤 개선도 보이지 않습니다.** 같은 문항 구성이라도 코퍼스가 작으면 검색 방식 네 가지가 모두 거의 같은 점수를 냅니다(DART 242청크에서 Recall@5가 0.93~1.00이었고, 11,022청크로 키우자 같은 문항의 순위 점수(MRR)가 0.10~0.22 내려갔습니다). 코퍼스를 다 모은 뒤에 v1을 동결하고, 일부러 어려운 문항을 넣으세요.

## 두 번에 나눠 동결합니다

| 버전 | 시점 | 건수 | 하는 일 |
|---|---|---|---|
| v1 | 11/3(화) | 30건 (관련 15, 비관련 15) | 사람이 정답을 판정하고 동결, 검색 베이스라인 점수 |
| v2 | 11/6(금) 중간 점검 전 | 50건 이상 (관련 25, 비관련 25) | v1의 관련 8건(1·3·5·7·10·11·13·15)과 비관련 15건을 가져오고 관련 17건·비관련 10건을 더해 2026-11-04 동결(`FROZEN.json`). 뺀 v1 관련 7건(2·4·6·8·9·12·14)은 `hardset_v1.jsonl`에 제외 사유와 함께 둔다. 검색 지표는 두 회사 비교 질문(31·32)을 뺀 23건으로 잰다(`mappings/dataset_v2.retrieval23.jsonl`) |

v2를 동결한 뒤에는 **단일 에이전트 기준 점수도 v2로 다시 재고**, 멀티에이전트와 이후 모든 개선 전후 비교를 v2로 잽니다.

## 파일과 형식

`dataset_v1.jsonl`에 형식 예시 2건이 있습니다. v2는 위 표의 v1 문항을 복사해 `dataset_v2.jsonl`로 만들어 건을 더합니다. 동결된 `dataset_v1.jsonl`은 그대로 둡니다.

| 필드 | 뜻 |
|---|---|
| `kind` | `relevant`(코퍼스에 답이 있다) 또는 `irrelevant`(주제 안이지만 코퍼스에 답이 없다. 거절이 정답) |
| `irrelevant_type` | 비관련만. 아래 4종 중 하나: `out_of_domain`, `unknown_entity`, `missing_attribute`, `wrong_period` |
| `as_of` | 정답 기준일. 코퍼스가 바뀌면 정답이 바뀌는 문항(최신 공시, 개정 법령)을 가려내는 근거 |
| `corpus_version` | 이 문항을 쓸 때의 코퍼스 버전(`data/manifest.jsonl`의 해시 또는 날짜) |
| `expected` | 정답 또는 판정 기준 |
| `gold_chunks` | 정답 근거가 있는 청크나 문서 위치. 비관련은 빈 목록. v2부터는 `gold_spans`에서 스크립트로 만든다 |
| `gold_spans` | v2부터. 정답 근거의 정본. 원문 span(문장 하나나 숫자 하나처럼 짧게)과 `rcept_no`·장·절·연결/별도 위치. 같은 내용이 여러 곳(II장·IV장·연결주석·별도주석)에 있으면 모두 적고, 다항목 질문은 항목(`item`)별로 따로 적는다. 비관련은 빈 목록 |
| `why` | 정답을 정한 기준. 팀원끼리 판단이 갈릴 때 돌아보는 근거 |

**잘 되는 것만 모으면 평가가 아니라 자랑입니다.** 비관련 질문, 애매한 질문, 말을 바꿔 묻는 질문을 반드시 넣으세요.

## 비관련 질문은 4종을 섞습니다

한 종류만 쓰면 쉬운 거절만 늘어 점수가 부풀려집니다. 비관련 절반 안에서 4종이 모두 들어가야 합니다.

| `irrelevant_type` | 뜻 | 예 (금융 공시 코퍼스) |
|---|---|---|
| `out_of_domain` | 도메인 밖 | "서울 날씨는?" |
| `unknown_entity` | 코퍼스에 없는 기업이나 대상 | 코퍼스에 없는 회사의 영업이익 |
| `missing_attribute` | 있는 대상이지만 코퍼스에 없는 항목 | 있는 회사의 코퍼스에 없는 항목 |
| `wrong_period` | 같은 공시인데 기간이 다름 | 3분기를 물었는데 코퍼스에는 2분기만 있음 |

## 질문은 정답을 보지 않고 씁니다

질문을 쓰는 사람은 정답 청크를 열어 보지 않고 질문을 씁니다. 정답을 보고 쓴 질문은 정답 문장의 낱말을 그대로 따라 쓰게 되어 검색이 쉬워집니다. 정답 청크는 다른 팀원이 나중에 찾아 `gold_chunks`에 적습니다.

## 팀 역할과 검수 순서

역할은 정본 `SPEC.md` 7장을 먼저 확인하고, 동결 전 검수는 `docs/specs/evaluation-governance.md`의 절차를 따른다.

| 담당 | 역할 |
|---|---|
| 서정현 | 질문 초안 작성, 평가 하네스 관리, 실패 문항 기록 |
| 류승민 | `expected`, `gold_chunks`, `why` 판정, 동결 전 검수·최종 확인 |
| 박민영 | 측정 결과 검토 |

1. 서정현은 `gold_chunks`와 `expected`를 보지 않고 질문 초안만 작성한다.
2. 류승민이 각 문항의 `expected`, `gold_chunks`, `why`를 판정하고 동결 전 구성과 형식을 검수·최종 확인한다. JSONL 필수 필드, 중복 `id`, 관련 문항의 `gold_chunks` 존재와 비관련 문항의 빈 `gold_chunks`를 확인한다. v1은 관련 15건·비관련 15건이며 비관련 4종을 모두 포함해야 하고, v2는 관련 25건·비관련 25건 이상이어야 한다.
3. 박민영은 측정 후 결과를 검토한다.
   - **v2 50건의 판정자(11/12 기록)**: v2의 `expected`·`gold_spans`·`why`는 박민영이 판정했다. 동결 때 문항별 판정자를 파일에 남기지 않아, 동결 파일은 그대로 두고 문항별 기록을 `evals/mappings/dataset_v2.judges.jsonl`에 따로 적었다(11/11 점검 의견 반영).
4. 동결 후 평가셋은 수정하지 않는다. 코퍼스 변경으로 제외할 문항은 `exclusions.json`에 기록한다.
5. 실험 전에는 `PREREGISTER.md`에 한 변경과 수치 기대 범위를 기록한다.

## 동결

```bash
python evals/freeze.py dataset_v1.jsonl     # sha256과 건수를 FROZEN.json에 기록
python evals/freeze.py --check              # 동결 이후 바뀐 파일이 없는지 확인
```

동결 뒤에는 정답을 고치지 않습니다. `tests/test_frozen_evals.py`가 PR마다 해시를 확인하고, 바뀌면 CI가 실패합니다. 정답이 정말 틀렸다면 파일을 고치지 말고 `docs/`에 이유를 적고 강사와 상의하세요.

### 동결 뒤에 코퍼스를 바꿨다면

코퍼스가 바뀌면 정답이 달라지는 문항이 생깁니다(DART 실험에서는 동결한 v1 30건 중 10건이 그랬습니다). 평가셋 파일은 고치지 않고 `evals/exclusions.json`에 문항 id와 사유를 적어 **지표에서만 뺍니다**. 사유를 공개하는 것이 조건이며, 제외 때문에 50건 밑으로 줄어도 감점하지 않습니다. `EVAL_REPORT.md` 2장에 제외 건수를 적으세요.

```json
{"as_of": "2026-11-08", "excluded": [{"id": 7, "reason": "신규 공시로 정답 청크가 바뀜"}]}
```

## 판정 방식

정확 일치, 스키마 통과, 규칙 기반, LLM-as-judge 모두 가능합니다. 다만 **어떤 방식이고 한계가 무엇인지** `EVAL_REPORT.md`에 적어야 합니다. 생성 모델과 판정 모델은 같은 것으로 두지 마세요. 후한 점수가 나옵니다.

청크 id가 일치하는지만 보면 "답이 질문에 맞는가"는 알 수 없습니다. 한계로 적으세요. 하나의 정확도로 합치지 말고 `EVAL_REPORT.md` 2장의 **지표 5개**로 나눠 보고합니다.

### 검색 지표 이름 (`backend/rag/evaluation.py`)

| 키 | 뜻 |
|---|---|
| `hit_at_k` | 상위 k개 안에 정답 청크가 **하나라도** 있는 관련 문항의 비율 |
| `recall_at_k` | 문항마다 정답 청크 중 상위 k개에 들어온 **비율**의 평균 |
| `mrr_at_k` | 첫 정답 순위의 역수 평균 |
| `ndcg_at_k` | 정답이 앞 순위일수록 큰 점수(1/log2(순위+1))를 준 값의 평균 |

정답 청크가 1개인 문항은 Hit와 Recall이 같고, 여러 개인 문항에서 갈립니다. **이 이름으로 바꾸기 전에 만든 `evals/results/*.metrics.json`의 `recall_at_k`는 Hit@k 값입니다.** `PREREGISTER.md`의 "Recall@10(=Hit@10)"도 같은 뜻입니다. 예전 결과 파일은 고치지 않고, 필요하면 원시 결과(`*.jsonl`)로 다시 계산합니다.

## 결과 보관

재측정 결과의 원시 파일은 `evals/results/`에 둡니다. 평가자가 샘플 몇 문항을 다시 돌려 숫자가 맞는지 보므로, **한 줄 재현 명령**을 `EVAL_REPORT.md` 9장에 적으세요.

검색 원시 결과는 평가셋의 모든 id를 정확히 한 번씩 포함합니다. 누락·중복·알 수 없는 id는 검색 실패로 조용히 세지 않고 입력 오류로 중단합니다.

```json
{"id": 1, "retrieved_chunks": ["chunk-a", "chunk-b"], "latency_ms": 12.3}
```

Recall@k와 MRR은 다음 명령으로 계산합니다. 출력에는 dataset과 원시 결과의 SHA-256도 함께 기록됩니다.

```bash
python -m backend.rag.evaluation \
  --dataset evals/dataset_v1.jsonl \
  --results evals/results/vector_v1.jsonl \
  --k 10 \
  --output evals/results/vector_v1.metrics.json
```

이 계산기는 검색 근거 청크의 순위만 평가합니다. 생성 답변의 정답 근거 인용률·오답 근거·과잉 거절·올바른 거절·환각 위험은 `EVAL_REPORT.md`의 별도 5개 축으로 측정합니다.
